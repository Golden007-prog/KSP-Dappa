# Round 2 · Phase 4 — decisions (officer tiers)

D-entries in docs/DECISIONS.md style, numbered D-phase4-N for the lead to renumber. Every fallback and judgment call in this workstream, with what the code actually returned.

**D-phase4-1 · The tier aggregates are computed in the API from CaseMaster / AggMonthly / StationRisk / HotspotCluster / AnomalyAlert, not from a new table (team, 28 Aug 2026).**
`GET /tiers/beat`, `/tiers/station` and `/tiers/state` (functions/dappa_api/lib/routes/tiers.js, registered in lib/app.js) derive every figure at read time over the existing ER tables, cached 300 s like the other read routes, and stamp `meta.provenance {asOn, window, method, provisional:true, tables}` on every answer in the Monthly Crime Review's own "provisional · as on" idiom. Why: the Round-2 ER schema is law and the Development Data Store already holds the rows; a materialised "tier" table would be a second source of truth that drifts. Measured through the stub harness: `/tiers/beat` 200 in 17 ms, `/tiers/station` 200 in 5 ms, `/tiers/state` 200 in 4 ms (functions/dappa_api/test/round2/phase4.test.mjs, 88 checks after the 29 Aug corrections; the suite read 870 / 870 when this was the only Round-2 file and 1360 passed / 1 failed at hand-over, the one failure being `WIRED search sends the documented query shape` in test/run.mjs:1329 against lib/search.js — both files uncommitted edits of another workstream, not touched here). On the deployed Development API the route is not yet live — `curl …/api/v1/tiers/beat` returned `{"ok":false,"error":{"code":"NOT_FOUND","message":"No route for GET /api/v1/tiers/beat"}}` on 28 Aug 2026 — so the lead's deploy is the switch-on.

**D-phase4-2 · "Usual level" is ONE Poisson-floored weekly mean shared by both tiers, and a station with no history reads NO DATA, never STABLE (team, 28 Aug 2026; corrected 29 Aug 2026).**
Both `/tiers/beat` and `/tiers/station` bucket the unit's trailing eight weeks of CaseMaster through the same `weekIndexOf()` helper and compare week 8 against the mean and spread of weeks 1–7; the swing (z) divides by `max(spread, √usual, 1)`. A unit with no rows answers 200 with empty arrays and `statusWord:'nodata'` (pinned by the phase-4 suite with a synthetic empty station '1099'), because a three-cases-a-week station must not be told it is "three swings above normal" over one extra FIR, and an unscored station must not be painted green. Why: docs/UX_RESEARCH.md §11.1 rule 3 ("call noise noise") and the colour-discipline rule that a status word is a claim.

**What was wrong and how it read.** The beat originally derived its usual from a *different* source — the 12-month AggMonthly mean divided by 365/12/7 — so the two tiers answered the same question with two numbers. Measured on the fixture before the fix, unit 1011, week 2026-08-10 → 2026-08-16, one FIR: `/tiers/beat` said "a usual 26 a week · ▼ FALLING" (usualPerWeek 26.3, swings −2.76) while `/tiers/station` said "a usual 0 — within the normal range · ✓ STABLE" (usualPerWeek 0.1, swings 0.90). Both baked demo snapshots carried those numbers, so a judge could open the two tabs and read opposite verdicts on one week. The CaseMaster seven-week mean won because it is the figure an SHO can check against the station diary; the AggMonthly figure survives on the beat as `recent.longRun {usualPerWeek, months:12, basis}`, labelled as a long-run comparison and wired to nothing — it sets no status word. Measured after the fix, same unit and week (now 5 FIRs against the richer fixture): both endpoints return usualPerWeek 1.1, swings 3.72, statusWord "rising". Pinned by six `one baseline (unitId)` checks per unit in `test/round2/phase4.test.mjs`, run over units 1011 and 1031 and over the empty station 1099.

**D-phase4-3 · Status words are computed once, server-side, from one rule (team, 28 Aug 2026).**
`statusFromZ`: z ≥ 3 → rising, 2 ≤ z < 3 → watch, z ≤ −2 → falling, else stable, null → nodata; pendency: > 60 d rising, > 30 d watch; risk word high/elevated/normal → rising/watch/stable. The client's lib/status.js repeats the same thresholds for values it derives itself (SLA state, hotspot activity). Every StatusPill renders colour + glyph + word (▲ ● ✓ ▼ —) and prints black; amber is used only for WATCH; forecast bands and the tier-switcher frame use the primary blue (design correction 2).

**D-phase4-4 · The tier switcher is presentation, anonymous lands on District, and a `?tier=` link wins over storage (team, 28 Aug 2026; extends D-015).**
`TierSwitcher` writes `useTierStore.setTier` and navigates to `TIER_HOME[tier]?tier=…`; `TierEyebrow` performs the once-per-session `GET /auth/me` read (`useAuthTier` → `applyRole`) so a signed-in Catalyst role opens on its tier, and a stored switcher choice still wins. Nothing in the switcher grants a capability; the tooltip says so ("Demo asset: changes what is shown first and how it is worded, never what you may do"). Desktop placement: the topbar at ≥ 1280 px (compact labels, full labels and the "Tier" eyebrow at ≥ 1536 px) because at 1280 px with the sidebar open the existing chrome leaves ~240 px; on phones both controls sit at the top of the More sheet at 44 px. Between 768 and 1279 px the controls are reachable only from the sidebar routes and the `?tier=` link — recorded as a gap.

**Correction (29 Aug 2026) — what `?tier=` actually moves, and the route now moves it too.** The demo note said "?tier=beat changes the eyebrow"; that is half true and worth pinning so the walkthrough does not point at the wrong thing. The tier homes carry their own fixed role eyebrow (`TierHeader` on /beat always renders `tier.eyebrow.beat` → "Beat · Head Constable", measured identical with and without `?tier=beat`). What `?tier=` moves is `TierEyebrow`, which renders only when `pathname === '/'` and `tier === 'district'`: `#/?tier=district` shows "Commissionerate · DCP (Crime)" and `#/?tier=beat` removes it and sets `documentElement.dataset.tier='beat'`. Separately, the nav entries are plain routes (`{ to: '/beat' }`), so reaching a tier home from the sidebar or the More sheet used to leave the store on 'district': `readPlain()` returned false and the Beat KPI tile rendered the technical term "seasonal baseline" instead of "Usual level". Only the `?tier=` deep link flipped it. `useTierRoute(tier)` (client/src/routes/tiers/bits.jsx) now sets the tier from the route in all three homes, which is what the switcher already did when it navigated there. Verified with Playwright at 360×640 on the static demo: land on `#/` (`dataset.tier` = "district"), open More, click "My beat" → `dataset.tier` = "beat", the tile reads "Usual level", and no technical label appears in the page text.

**D-phase4-5 · The Beat dismiss writes to the Phase-7 action log when an alert exists, otherwise to the phone, and always says which (team, 28 Aug 2026).**
`POST /alerts/:alertKey/actions` (lib/routes/actionlog.js) requires a dismiss `reason` from a fixed list, so the officer's free-text reason travels as `reason:'other'` + `note`, with `actorRole` = the current tier and `source:'tier-home'`; the primary "patrol tonight" action is recorded as a `note`. When the station has no open alert there is no subject key, and when the POST fails (offline, 4xx) the record is kept in `localStorage['dappa-tier-actions']` and the card shows "Saved on this phone only — the action log endpoint is not wired yet". A dismiss is never dropped silently. Not verified live: the Development API does not yet carry the Phase-7 route either (same deploy).

**D-phase4-6 · Offline beat card = last good answer in localStorage + a hand-written service worker; no Workbox (team, 28 Aug 2026).**
`Beat.jsx` stores the last successful `/tiers/beat` body per station and renders it when the query errors or `navigator.onLine` is false, with a "Saved copy from <time> · offline" pill (`role=status`). `client/public/sw.js` precaches the shell, serves navigations network-first with the cached index as fallback, static assets cache-first, and API GETs network-first with a 4 s timeout and a stamped last-good copy (`X-Dappa-Cache: saved <iso>`); it is registered only in production builds with `${import.meta.env.BASE_URL}sw.js`, so '/', '/app/' and the Pages base all resolve. **Corrected 29 Aug 2026:** `SHELL` and `ASSETS` were template-keyed on `VERSION` but the API cache was the literal `'dappa-api-v1'`, and `activate` keeps any key equal to SHELL/ASSETS/API — so the header's "Bump VERSION to invalidate every cache" was false for saved API answers, and a deploy that changed a payload shape would have served the old shape offline. `API` is now `\`dappa-api-${VERSION}\``; the cost is that a version bump drops the saved offline answers, which the Beat card's own localStorage copy covers until the next successful online load. Why two layers: the in-page copy works even where a worker is blocked (private mode, first visit) and the worker keeps the shell and every other GET. Icons: four PNGs drawn with Pillow from the favicon's shield (192/512, any + maskable). Not verified: install prompt on a real Android device; verified: the manifest parses and the build serves `sw.js` and `icons/*` from the public root.

**D-phase4-9 · The fixture WAS extended for the tier screens, and the pinned counts moved with it (team, 28 Aug 2026; reversed 29 Aug 2026).**
The original call was to leave the fixture alone because the contract suite pins CaseMaster at 40 rows in several places. The consequence was worse than the cost: `/tiers/station` returned `caseload: []`, `series: []` and `undetected30.count: 0` for **every** unit on the fixture — unit 1011, the station both tier endpoints default to (StationRisk scores it highest), had two CaseMaster rows in total and the Employee table had one row — so the baked static demo showed the Station console's three headline cards empty, and the three contract checks that should have caught it were `.every()` calls over empty arrays and passed.

`buildFixtureTables()` now appends twelve `TIER_CASES` rows at unit 1011 (ids 101–112), dated backwards from the unit's own last registration (`${NOW_YM}-16`, still the tier "as on") so each lands in a known weekly bucket whatever month the fixture is built in, plus two more Employee rows and their ranks, and one Victim and one Accused per new case from the existing name pools so the link graph keeps its single component. Measured on the rebuilt fixture, unit 1011: weekly buckets [1,1,1,1,1,1,2,5] → usual 1.1, swings 3.72, ▲ RISING; series = one run of 3 Chain Snatching cases across 9 days, all at night; undetected30 = 4 property cases still under investigation, oldest 95 days; caseload = 3 named officers (4 / 3 / 2 open) with one ▲ RISING on a >60-day case; beat openCases 9 with 4 over 30 days.
