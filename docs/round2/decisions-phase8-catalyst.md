# Round 2 · Phase 8 — decisions (new Catalyst service surfaces)

D-entries in docs/DECISIONS.md style; the lead renumbers. Every Catalyst call below was made from `catalyst serve --http 3106 --only functions:dappa_api` on 28 Aug 2026 against the linked Development project (SDK initialised: `/healthz` read 45,000 CaseMaster rows live), unless the entry says otherwise.

**D-phase8-1 · Data Store OLAP is wired and exercised, and it is not enabled (phase 8, 28 Aug 2026).**
`app.zcql().executeOLAPQuery(sql)` exists only in the 3.4.0 typings (its docs page is 404), so `lib/olap.js` was made to prove itself rather than be believed: `GET /meta/olap-benchmark` runs the district × head × month cube both ways. Measured: ZCQL leg 1,027 ms, 3,006 rows, 11 pages, not truncated; OLAP leg failed in 43 ms with the exact server message `OLAP System is not available`. That is the console step (Data Store ▸ OLAP Database ▸ Enable), not a code fault, so the row reads `console-pending` until `OLAP_ENABLED` attests the step and the flag path serves; one failure marks the engine unhealthy for the container's life so the pending state costs one round trip, not one per request. `/olap/cube` on the same window answered in 890 ms through ZCQL with `meta.engine:"zcql"` and the reason in `note`. Whether OLAP shares ZCQL's 300-row cap is unknown; a result of exactly 300 rows is flagged `possiblyCapped`.

**D-phase8-2 · The heavy aggregates route through `olap.queryAll`; `/tiers/state` is left for the lead (phase 8, 28 Aug 2026).**
The nightly detect step in `lib/circuits.js` (38 districts × 8 heads × 12 months) now calls `olap.queryAll(ctx, q, { maxRows })` and takes `.rows`; the fallback is the same paged read as before. `lib/routes/tiers.js` was untracked and being written by phase 4 during this run, so it was not edited. The swap is one line in `stateHome`: replace `ctx.ds.queryAll({...triad...}, { maxRows: 2000 })` with `(await olap.queryAll(ctx, {...triad...}, { maxRows: 2000 })).rows` and add `engine: olap.olapState().healthy ? 'olap' : 'zcql'` to the meta, after phase 4 lands.

**D-phase8-3 · Zia OCR was silently failing on every scan because of the temp-file extension (phase 8, 28 Aug 2026).**
The first three live OCR calls (fir_01–03, `language:'eng'`) all came back `ocrAvailable:false, source:'fallback-local'` with no reason — `lib/zia.js ocrScan` wrote the upload to `dappa-ocr-*.img` and swallowed the error. Zia types the upload from the file name. The fix sniffs the magic bytes (png/jpeg/webp/gif/bmp/tiff/pdf) for the extension, attaches an error listener to the read stream, and puts the failure text into the fallback `note`. Retest on fir_01 with `language` omitted (auto-detect): `source:'zia-ocr'`, `confidence: 97`, 782 characters; the English body read cleanly ("The complainant Lakshmamma Gowda, aged 52, resident …", "gold mangalsutra", "Rs. 1,45,000", "14-07-2026") and the extractor produced `weapon:knife`, `vehicle:two-wheeler`, `item:gold-mangalsutra`; the Kannada header line came back as Latin garbage (`dJodododdo:0dadaba3Sab …`) under auto-detect. A `language:'kan'` pass was not spent (budget, D-phase8-6). The retest image had its right margin clipped by the generator (75-character lines at a 30 px mono face on a 992 px page); the generator was corrected to 22 px afterwards (a 75-character line is now 900 px), which explains the truncated words in the quoted text — the ground-truth manifest was never wrong.

**D-phase8-4 · Zia Object Recognition does not see procedural drawings; the panel says so (phase 8, 28 Aug 2026).**
`detectObject` on the knife scene (scene_03) returned no objects; on the two-wheeler scene (scene_02) it returned one object, `scissors`, confidence 0.4955, box [250,191,762,490] — the wrong class over roughly the right region. Both calls answered in about 2.9 s. So the demo runs in fixture mode by default: the tags are the shapes `pipeline/scenes_generate.py` drew, `meta.source:"fixture"`, dashed amber boxes and a note on the card; when Zia does answer the boxes go solid teal with its confidence, and an empty Zia answer is shown as "nothing was recognised", never back-filled from the manifest. The object → MO mapping (`object:<class>` plus `weapon:`/`vehicle:`/`item:` families, merged with the narrative's MO tags per case) is the same on either path. Photographic scenes would change the result; none are used because every image in this project is generated.

**D-phase8-5 · Weapons and injury flag an upload for review; only explicit content blocks it (phase 8, 28 Aug 2026).**
`lib/moderation.js` turns Zia Image Moderation probabilities into allow / review / block. Live: the knife scene scored `weapon: 1.0`, `prediction: unsafe_to_use` → `review`; the handbag scene scored all categories 0, `safe_to_use` → `allow`. A police evidence platform that blocked weapons would block the evidence, so the thresholds are weapon/violence/gore ≥ 0.6 and drugs ≥ 0.7 → review, nudity/explicit ≥ 0.7 → block; the fallback verdict is `unscreened` with a format/size check, never `allow`. `guardUpload()` is the one call every image route makes (OCR page, scenes, phase 6's probe upload).

**D-phase8-6 · Nine Zia calls against a budget of eight (phase 8, 28 Aug 2026).**
Spent: OCR 3 (all failed, D-phase8-3) + OCR retest 1 + objects 2 (each 1 moderation + 1 detect = 4) + moderation 1 = 9 pooled Zia calls. The one-call overrun bought the finding that OCR works at all; without it the feature would have shipped labelled "unreachable". No further Zia call was made after the retest. **D-phase8-7 · Job Scheduling replaces Circuits; the pool exists and a live submit was deliberately not made (phase 8, 28 Aug 2026).**
`getAllJobpool()` returned one console pool: `dappanightly` (id `50643000000453771`, type Function, memory 512). `lib/jobs.js` submits `{ target_type:'Function', target_name:'dappa_nightly', jobpool_name, params, job_config:{ number_of_retries:2, retry_interval:900 } }` and reads `getJob` back; with `JOB_POOL_NAME` unset the same three steps ran inline in 1,083 ms (aggregate 124 ms · detect-anomalies 913 ms, 304 series scanned, 28 candidates, 39 open alerts · notify 46 ms dry-run) and were reported in the job shape. `submitJob` was not exercised live because it runs the real Python nightly against the shared Development Data Store while six other workstreams were testing on it; the lead sets `JOB_POOL_NAME=dappanightly` and submits once from the About card. The Circuits row now names Job Scheduling as its fallback.

**D-phase8-8 · SmartBrowz `takeScreenshot` needs a user context this runtime lacks (phase 8, 28 Aug 2026).**
`POST /reports/map-snapshot` with `page_options.viewport 1280×800`, `screenshot_options.type png`, `navigation_options.wait_until networkidle2` failed in 99 ms with `No such User with the given id exists` — the same error the brief PDF path documents for `convertToPdf` under an anonymous call, so the option keys were not the problem (that error reads "either the request body or parameters is in wrong format"). The static command-dashboard image stands in, labelled `mode:'static'` with the reason, and the Weekly Brief carries it as `mapSnapshot`. A bare no-options probe was not spent.

**D-phase8-9 · The OCR attach is an ActionLog note in phase 7's vocabulary, written by its own insert (phase 8, 28 Aug 2026).**
Live: `POST /ocr/attach` inserted ROWID `50643000000474001` into the Development ActionLog through `datastore().table('ActionLog').insertRows` and `GET /ocr/attachments?caseId=1` read it back by ZCQL in 53 ms. The row uses phase 7's subject key `case:<id>` and `ActionType:'note'` so the case timeline lists it like any officer note; phase 7's `recordAction()` was not called because its validator builds the Payload itself and would drop the recovered text, confidence and MO tags. CaseMaster is never written. Off-Catalyst the row lives in a bounded memory list mirrored to the cache.

**D-phase8-10 · APM and Logs are console surfaces; the health card measures the function itself (phase 8, 28 Aug 2026).**
The 3.4.0 SDK exposes no read API for APM or Logs; its vendored `lib/apminsight` is the Site24x7 agent (README verified) and needs a Site24x7 licence key, which is not a Catalyst credential. `GET /meta/observability` therefore serves a 500-request ring buffer (live sample after the probes: 19 requests, p50 167 ms, p95 2,872 ms — the Zia object calls — 0 errors) and says on the card that APM/Logs are read in the console; `APM_ENABLED` is the operator's attestation that APM was switched on.

**D-phase8-11 · Embedded sign-in loads Zoho's own SDK from Zoho's CDN, and stays off in the tracked configuration (phase 8, 28 Aug 2026).**
Catalyst's embedded authentication is `catalyst.auth.signIn(elementId)` from `catalystWebSDK.js` on static.zohocdn.com plus `/__catalyst/sdk/init.js` from the app host. The rule against CDN scripts exists to keep third parties out; this script *is* the Catalyst service. It is still gated twice — `FEATURE_AUTH_EMBED` (off by default, `""` in the tracked config) and a `.catalystserverless.*` hostname — so the judged deployment loads nothing external unless the lead turns it on after creating the officer roles. `PUBLIC_DEMO` writes keep the documented demo token; the token is kept per tab in sessionStorage and sent only on the attach request.

**D-phase8-12 · The officer tier is a server-side claim mirrored from the client's rules (phase 8, 28 Aug 2026).**
`GET /auth/me` now carries `tier`, computed from `role_details.role_name` by the same patterns as `client/src/lib/tier.js` (Constable → beat, SHO/PSI → station, SP/DSP → district, DGP/admin → state; anonymous → district) so phase 4's `applyRole` can read one field. Invites go through `registerUser` with the tier's console role id (`AUTH_ROLE_ID_<TIER>`); without the id the endpoint reports `console-pending` instead of inventing one. D-015 stands: the tier is presentation, not authorisation.

**D-phase8-13 · The AutoML challenger's AUC is typed in from the console, never computed here (phase 8, 28 Aug 2026).**
`POST /predict/outcome/challenger` scores the QuickML AutoML endpoint beside the embedded logistic champion and reports agreement; its AUC comes only from `QUICKML_AUTOML_AUC`, the figure the operator copies from the pipeline's evaluation tab, so a number on screen is always one a judge can find in the console. Off-flag the champion serves alone with `status:'disabled'`.

**D-phase8-14 · The LLM may phrase but cannot invent: the numeric firewall (phase 8, 28 Aug 2026).**
`lib/composer.js` collects every number reachable in the deterministic answer and chart (canonicalised: commas and % stripped, three decimals), then rejects the LLM reply if any number in it is missing from that set, with integers ≤ 12 allowed as prose ("top 5", "last 3 months"). A rejected composition ships the deterministic sentence with the offending tokens listed; a failed call ships it with the reason. The prompt carries the tier (beat = one plain sentence) and the caste/religion and "predicts a crime" prohibitions. No LLM endpoint exists yet, so the path was exercised only through the contract suite's stubbed fetch.

**D-phase8-15 · `catalyst serve` was pointed at the installed Node 25 (phase 8, 28 Aug 2026).**
The CLI (1.27.0) refuses to serve a node20 function without a `node20.bin` entry; the workstation has only Node 25.2.1. `catalyst config:set node20.bin="C:\Program Files\nodejs\node.exe"` made local serving possible and every live figure above comes from it. The deployed function still runs Node 20; nothing in this phase uses a Node 25-only API. The lead can revert with `catalyst config:set node20.bin=` (empty).

**D-phase8-16 · Stratus pre-signed links fall back to the API proxy (phase 8, 28 Aug 2026).**
`GET /reports/artifacts/:id/url` mints `generatePreSignedUrl(key,'GET',{expiryIn})` only for Stratus-stored artefacts; memory and File Store artefacts, and any signing failure (the same user-context error as D-phase8-8), return the `/reports/artifacts/:id` path as `mode:'api-proxy'` so a link never dangles.

**D-phase8-17 · Tier cards get a documented cache helper rather than a new segment (phase 8, 28 Aug 2026).**
`lib/tiercache.js` wraps `ctx.cache.wrap` with `v1:tiers:<tier>:<unit>` keys at 300 s in the existing `dappa` segment; a dedicated console segment is optional via `CACHE_TIER_SEGMENT`. Creating a second segment would add a console step for no measurable gain at this traffic, and the oversized-value guard in `lib/cache.js` already protects the shared segment.
