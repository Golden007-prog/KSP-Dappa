# Round 2 · Phase 8 — decisions (new Catalyst service surfaces)

D-entries in docs/DECISIONS.md style; the lead renumbers. Every Catalyst call below was made from `catalyst serve --http 3106 --only functions:dappa_api` on 28 Aug 2026 against the linked Development project (SDK initialised: `/healthz` read 45,000 CaseMaster rows live), unless the entry says otherwise.

**D-phase8-1 · Data Store OLAP is wired and exercised, and it is not enabled (phase 8, 28 Aug 2026).**
`app.zcql().executeOLAPQuery(sql)` exists only in the 3.4.0 typings (its docs page is 404), so `lib/olap.js` was made to prove itself rather than be believed: `GET /meta/olap-benchmark` runs the district × head × month cube both ways. Measured: ZCQL leg 1,027 ms, 3,006 rows, 11 pages, not truncated; OLAP leg failed in 43 ms with the exact server message `OLAP System is not available`. That is the console step (Data Store ▸ OLAP Database ▸ Enable), not a code fault, so the row reads `console-pending` until `OLAP_ENABLED` attests the step and the flag path serves; one failure marks the engine unhealthy for the container's life so the pending state costs one round trip, not one per request. `/olap/cube` on the same window answered in 890 ms through ZCQL with `meta.engine:"zcql"` and the reason in `note`. Whether OLAP shares ZCQL's 300-row cap is unknown; a result of exactly 300 rows is flagged `possiblyCapped`.

**D-phase8-2 · The heavy aggregates route through `olap.queryAll`; `/tiers/state` is left for the lead (phase 8, 28 Aug 2026).**
The nightly detect step in `lib/circuits.js` (38 districts × 8 heads × 12 months) now calls `olap.queryAll(ctx, q, { maxRows })` and takes `.rows`; the fallback is the same paged read as before. `lib/routes/tiers.js` was untracked and being written by phase 4 during this run, so it was not edited. The swap is one line in `stateHome`: replace `ctx.ds.queryAll({...triad...}, { maxRows: 2000 })` with `(await olap.queryAll(ctx, {...triad...}, { maxRows: 2000 })).rows` and add `engine: olap.olapState().healthy ? 'olap' : 'zcql'` to the meta, after phase 4 lands.

**D-phase8-3 · Zia OCR was silently failing on every scan because of the temp-file extension (phase 8, 28 Aug 2026).**
The first three live OCR calls (fir_01–03, `language:'eng'`) all came back `ocrAvailable:false, source:'fallback-local'` with no reason — `lib/zia.js ocrScan` wrote the upload to `dappa-ocr-*.img` and swallowed the error. Zia types the upload from the file name. The fix sniffs the magic bytes (png/jpeg/webp/gif/bmp/tiff/pdf) for the extension, attaches an error listener to the read stream, and puts the failure text into the fallback `note`. Retest on fir_01 with `language` omitted (auto-detect): `source:'zia-ocr'`, `confidence: 97`, 782 characters; the English body read cleanly ("The complainant Lakshmamma Gowda, aged 52, resident …", "gold mangalsutra", "Rs. 1,45,000", "14-07-2026") and the extractor produced `weapon:knife`, `vehicle:two-wheeler`, `item:gold-mangalsutra`; the Kannada header line came back as Latin garbage (`dJodododdo:0dadaba3Sab …`) under auto-detect. A `language:'kan'` pass was not spent (budget, D-phase8-6). The response now reports `language:'auto'` when the caller sent none — it used to echo the local default `'eng'`, which would have told an officer that a Kannada header had been read as English. The retest image had its right margin clipped by the generator (75-character lines at a 30 px mono face on a 992 px page); the generator was corrected to 22 px afterwards (a 75-character line is now 900 px), which explains the truncated words in the quoted text — the ground-truth manifest was never wrong.

**D-phase8-4 · Zia Object Recognition does not see procedural drawings; the panel says so (phase 8, 28 Aug 2026).**
`detectObject` on the knife scene (scene_03) returned no objects; on the two-wheeler scene (scene_02) it returned one object, `scissors`, confidence 0.4955, box [250,191,762,490] — the wrong class over roughly the right region. Both calls answered in about 2.9 s. So the demo runs in fixture mode by default: the tags are the shapes `pipeline/scenes_generate.py` drew, `meta.source:"fixture"`, dashed amber boxes and a note on the card; when Zia does answer the boxes go solid teal with its confidence. Two corrections after the phase-8 verification: (a) the leg was UNREACHABLE from the shipped client, because `EvidenceTags.jsx` posts `{sceneId, caseId}` with no bytes and the function's assets held only the manifest — the three scene PNGs now ship in `functions/dappa_api/assets/scenes/` and the route reads the named one when the flag is on, so `{sceneId}` alone exercises Zia; (b) an empty Zia answer on a KNOWN demo scene now shows the drawn boxes as the fixture they are (`source:"fixture"`, `ziaRan:true`, `ziaObjects:0`, and a note saying Zia recognised nothing) rather than an empty card — a drawn box is never re-labelled as Zia's, which is what "never back-filled" was protecting. On an arbitrary upload an empty answer is still reported as "nothing was recognised", because there is no manifest to fall back to. A separate bug made the fixture path claim a confidence it never had: `Number(null)` is 0, so every drawn box rendered "0 out of 100 sure"; `normaliseObjects` now guards before coercing and a drawn box carries `confidence:null`. The object → MO mapping (`object:<class>` plus `weapon:`/`vehicle:`/`item:` families, merged with the narrative's MO tags per case) is the same on either path. Photographic scenes would change the result; none are used because every image in this project is generated.

**D-phase8-5 · Weapons and injury flag an upload for review; only explicit content blocks it (phase 8, 28 Aug 2026).**
`lib/moderation.js` turns Zia Image Moderation probabilities into allow / review / block. Live: the knife scene scored `weapon: 1.0`, `prediction: unsafe_to_use` → `review`; the handbag scene scored all categories 0, `safe_to_use` → `allow`. A police evidence platform that blocked weapons would block the evidence, so the thresholds are weapon/violence/gore ≥ 0.6 and drugs ≥ 0.7 → review, nudity/explicit ≥ 0.7 → block; the fallback verdict is `unscreened` with a format/size check, never `allow`. `guardUpload()` is the one call every image route makes (OCR page, scenes, phase 6's probe upload).

**D-phase8-7 · Job Scheduling replaces Circuits; the pool exists and a live submit was deliberately not made (phase 8, 28 Aug 2026).**
`getAllJobpool()` returned one console pool: `dappanightly` (id `50643000000453771`, type Function, memory 512). `lib/jobs.js` submits `{ target_type:'Function', target_name:'dappa_nightly', jobpool_name, params, job_config:{ number_of_retries:2, retry_interval:900 } }` and reads `getJob` back; with `JOB_POOL_NAME` unset the same three steps ran inline in 1,083 ms (aggregate 124 ms · detect-anomalies 913 ms, 304 series scanned, 28 candidates, 39 open alerts · notify 46 ms dry-run) and were reported in the job shape. `submitJob` was not exercised live because it runs the real Python nightly against the shared Development Data Store while six other workstreams were testing on it. The tracked config therefore keeps `JOB_POOL_NAME` EMPTY (it briefly shipped as `dappanightly`, which armed the live submit branch on a path that has never executed once, and made the service table read `active — flag on and configured` for it). With the name blank the row reads `console-pending — flag on but JOB_POOL_NAME not set`, and the inline path renders the identical job shape, so the demo is unaffected. The lead arms it by setting `JOB_POOL_NAME=dappanightly` in the console env AFTER one successful manual submit from the About card, and confirms the pool accepts a cron-type function as `target_name` before the judged run. The Circuits row now names Job Scheduling as its fallback.

**D-phase8-8 · SmartBrowz `takeScreenshot` needs a user context this runtime lacks (phase 8, 28 Aug 2026).**
`POST /reports/map-snapshot` with `page_options.viewport 1280×800`, `screenshot_options.type png`, `navigation_options.wait_until networkidle2` failed in 99 ms with `No such User with the given id exists` — the same error the brief PDF path documents for `convertToPdf` under an anonymous call, so the option keys were not the problem (that error reads "either the request body or parameters is in wrong format"). The static command-dashboard image stands in, labelled `mode:'static'` with the reason, and the Weekly Brief carries it as `mapSnapshot`. A bare no-options probe was not spent. Two corrections after verification: (a) `captureMapSnapshot` was called only INSIDE the successful-PDF branch, so in the mode this deployment actually takes — `renderBrief` throwing the user-context error — the brief carried no `mapSnapshot` at all, not even the stand-in; it is now taken before the branch and rides on both the `pdf` and the `print-css` payload, through the same 6 h cache key the standalone route uses so the extra leg costs at most one render per district per 6 h. (b) `POST /reports/map-snapshot` had no guard while spending a metered render and minting a new timestamped Stratus object per call, and `?nocache=1` was honoured on a POST, so an anonymous loop was five renders and five objects. It is now behind `requireAdmin` like the other write-ish routes, `?nocache` is ignored on it (`meta.nocacheHonoured:false` says so), and the object key is `briefs/map-<district>-<yyyymmddhh>.png` in IST so a repeat inside the hour overwrites one object. Nothing in the client calls the route, so the guard costs no surface.

**D-phase8-10 · APM and Logs are console surfaces; the health card measures the function itself (phase 8, 28 Aug 2026).**
The 3.4.0 SDK exposes no read API for APM or Logs; its vendored `lib/apminsight` is the Site24x7 agent (README verified) and needs a Site24x7 licence key, which is not a Catalyst credential. `GET /meta/observability` therefore serves a 500-request ring buffer (live sample after the probes: 19 requests, p50 167 ms, p95 2,872 ms — the Zia object calls — 0 errors) and says on the card that APM/Logs are read in the console; `APM_ENABLED` is the operator's attestation that APM was switched on.

**D-phase8-11 · Embedded sign-in loads Zoho's own SDK from Zoho's CDN, and stays off in the tracked configuration (phase 8, 28 Aug 2026).**
Catalyst's embedded authentication is `catalyst.auth.signIn(elementId)` from `catalystWebSDK.js` on static.zohocdn.com plus `/__catalyst/sdk/init.js` from the app host. The rule against CDN scripts exists to keep third parties out; this script *is* the Catalyst service. It is still gated twice — `FEATURE_AUTH_EMBED` (off by default, `""` in the tracked config) and a `.catalystserverless.*` hostname — so the judged deployment loads nothing external unless the lead turns it on after creating the officer roles. `PUBLIC_DEMO` writes keep the documented demo token; the token is kept per tab in sessionStorage and sent only on the attach request.

**D-phase8-12 · The officer tier is a server-side claim mirrored from the client's rules (phase 8, 28 Aug 2026).**
`GET /auth/me` now carries `tier`, computed from `role_details.role_name` by the same patterns as `client/src/lib/tier.js` (Constable → beat, SHO/PSI → station, SP/DSP → district, DGP/admin → state; anonymous → district) so phase 4's `applyRole` can read one field. Invites go through `registerUser` with the tier's console role id (`AUTH_ROLE_ID_<TIER>`); without the id the endpoint reports `console-pending` instead of inventing one. D-015 stands: the tier is presentation, not authorisation.

**D-phase8-13 · The AutoML challenger's AUC is typed in from the console, never computed here (phase 8, 28 Aug 2026).**
`POST /predict/outcome/challenger` scores the QuickML AutoML endpoint beside the embedded logistic champion and reports agreement; its AUC comes only from `QUICKML_AUTOML_AUC`, the figure the operator copies from the pipeline's evaluation tab, so a number on screen is always one a judge can find in the console. Off-flag the champion serves alone with `status:'disabled'`.

**D-phase8-14 · The LLM may phrase but cannot invent: the numeric firewall (phase 8, 28 Aug 2026).**
`lib/composer.js` collects every number reachable in the deterministic answer and chart (canonicalised to three decimals with commas dropped, and TYPED: `42` and `42%` are different tokens, so the model cannot restate a raw count as a share or the reverse), then rejects the LLM reply if any number in it is missing from that set. The exemption is deliberately narrow after a probe got a fabrication through: a small integer passes ONLY when it is doing ordering or window work in the sentence — `top|first|last|next|previous|past N`, or `N of` / `N out of` — and is 0–12. Anywhere else an integer is rejected whatever its size, because 0–12 is exactly the range the police-relevant counts live in: with the old blanket "≤ 12 is prose" rule, a stub answering "There were 7 arrests and 11 chargesheets this month" against facts containing neither number returned `engine=quickml-llm, passed=true, rejected=[]` — the fabricated sentence was served to the officer as the answer. The cost of the narrow rule is a false reject (a legitimate "2 of the districts" phrasing that no ordering word marks), which ships the deterministic sentence — the safe direction. A rejected composition ships the deterministic sentence with the offending tokens listed; a failed call ships it with the reason. The prompt carries the tier (beat = one plain sentence) and the caste/religion and "predicts a crime" prohibitions. No LLM endpoint exists yet, so the path was exercised only through the contract suite's stubbed fetch.

**D-phase8-15 · `catalyst serve` was pointed at the installed Node 25 (phase 8, 28 Aug 2026).**
The CLI (1.27.0) refuses to serve a node20 function without a `node20.bin` entry; the workstation has only Node 25.2.1. `catalyst config:set node20.bin="C:\Program Files\nodejs\node.exe"` made local serving possible and every live figure above comes from it. The deployed function still runs Node 20; nothing in this phase uses a Node 25-only API. The lead can revert with `catalyst config:set node20.bin=` (empty).

**D-phase8-16 · Stratus pre-signed links fall back to the API proxy (phase 8, 28 Aug 2026).**
`GET /reports/artifacts/:id/url` mints `generatePreSignedUrl(key,'GET',{expiryIn})` only for Stratus-stored artefacts; memory and File Store artefacts, and any signing failure (the same user-context error as D-phase8-8), return the `/reports/artifacts/:id` path as `mode:'api-proxy'` so a link never dangles.

**D-phase8-17 · Tier cards get a documented cache helper rather than a new segment (phase 8, 28 Aug 2026).**
`lib/tiercache.js` wraps `ctx.cache.wrap` with `v1:tiers:<tier>:<unit>` keys at 300 s in the existing `dappa` segment; a dedicated console segment is optional via `CACHE_TIER_SEGMENT`. Creating a second segment would add a console step for no measurable gain at this traffic, and the oversized-value guard in `lib/cache.js` already protects the shared segment.

**D-phase8-18 · A service row says what a live probe found, not only that the flag is set (phase 8, 29 Aug 2026).**
`gated()` answered `active — flag on and configured` for `zia-vision` and `smartbrowz`, both of which this phase proved do not work as this app uses them. A row that is wired and configured and still cannot do the job is exactly what the servicemap header promises to disclose, so `probed(gated(...), note)` appends the measured result to an `active` reason and leaves `flag-gated` / `console-pending` alone: `zia-vision` now carries D-phase8-4's negative (nothing on scene_03, the wrong class on scene_02 — so the panels serve manifest tags labelled `source:fixture`; the moderation leg answered correctly and is called out separately), and `smartbrowz` carries D-phase8-8's (both call sites need a user context this runtime lacks). `node scripts/gen_service_table.mjs --check` passes with the regenerated README block and `docs/service_table.json`. On the DC matrix: `docs/CATALYST_SERVICE_RESEARCH.md` reads Job Scheduling as inferred-available in IN; D-phase8-7's live `getAllJobpool()` listing the `dappanightly` pool from the IN project settles it as available — the "EU, AU, IN, or CA" sentence quoted from the jobs intro applies to the Circuit target, which is what remains unavailable.

**D-phase8-19 · The two anonymous Zia routes get a cache and a budget, not an auth guard (phase 8, 29 Aug 2026).**
`POST /reports/map-snapshot` could take `requireAdmin` because nothing in the client calls it (`grep -rn "map-snapshot\|mapSnapshot" client/src` returns nothing). `POST /zia/objects` and `POST /zia/moderate` cannot: the first is what the FIR-detail evidence card calls for an anonymous judge, the second is the OCR page's intake guard, and guarding either would remove a scored surface from the demo. The generic limiter (600 req/min/IP) is no protection for a metered call, so they get two cheaper controls instead. The scene path of `/zia/objects` — the only one a judge triggers by browsing — is cached 6 h on `v1:zia-objects:<sceneId>:<caseId>`, so three scenes cost at most three Zia calls per container rather than one per FIR view; an uploaded image is never cached. Both routes then share a per-IP hourly ceiling, `AI_BUDGET_PER_HOUR` (default 40, surfaced as `X-AI-Budget-Remaining`, `429 AI_BUDGET` past it) which a judge cannot reach by clicking but a loop trips in seconds. `POST /copilot/compose` and `POST /predict/outcome/challenger` are left open: with `QUICKML_LLM_URL` and `QUICKML_AUTOML_ENDPOINT_KEY` empty in the tracked config neither leaves the container today, and when the lead sets them the same helper is one line per route.
