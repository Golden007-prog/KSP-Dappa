# Phase 7 decisions — action loop and audit trail (28 Aug 2026)

Entries in `docs/DECISIONS.md` style; the lead renumbers `D-phase7-N` into the D-0NN sequence.

**D-phase7-1 · ActionLog writes go through the SDK when deployed and a per-container memory store otherwise; reads merge both and name the engine (phase 7, 28 Aug 2026).**
`lib/actionlog.js recordAction` calls `require('zcatalyst-sdk-node').initialize(req)` and `datastore().table('ActionLog').insertRow(row)` — the same write pattern as `POST /admin/bulk-insert`. Outside Catalyst the SDK throws `Failed to parse object` (verified with a bare `{headers:{}}` request against the installed 3.4.0), so the row is kept in a module-level Map and `meta.storage` says `memory`, `meta.source` says `local`. Reads (`listActions`) go through `ctx.ds.queryAll` on `ActionLog` like every other table; in PUBLIC_DEMO a failed ZCQL read is answered from the fixture, and the fallback counter (`getFallbackState().queries`) is what lets the response say `fixture` rather than `datastore`. Memory rows are merged into every read, deduped on the idempotency key, so a demo decision is visible on the next request whichever engine answered. A memory row evaporates with the container; the response tells the officer so ("recorded for this session only"). Nothing is ever deleted — dismiss writes a row and, when allowed, sets `AnomalyAlert.Status = 'DISMISSED'`; the alert row stays.

**D-phase7-2 · Anyone may record a decision; only an authenticated or admin-token caller may flip `AnomalyAlert.Status` (phase 7).**
The record is the audit trail, and an anonymous judge must be able to make one, so `POST /alerts/:alertKey/actions` is not behind `requireAdmin`. The actor is resolved in this order — Catalyst Authentication session (`lib/auth.js whoami`, `actorSource:'catalyst-auth'`), the demo admin token (`admin-token`), the tier switcher's role plus a client-supplied display name (`client`, default `anonymous`) — and stored in `Payload.actorSource` so a seeded, anonymous and signed-in decision can never be confused. The existing rule that PUBLIC_DEMO is read-only for `AnomalyAlert` (`/alerts/:id/ack`, D-015) is kept: acknowledge/dismiss mutate `Status` only when `canMutateStatus`, and the response carries `statusUpdated` and a `statusReason` the client shows as a toast. `canMutateStatus` is now simply `false` on the anonymous branch. It used to be `!ctx.flags.publicDemo`, which made this entry's own title untrue with PUBLIC_DEMO off: an unauthenticated POST would have run the `UPDATE AnomalyAlert`. Harmless on the tracked config (PUBLIC_DEMO is "true") but wrong in a real deployment, where the demo flag is the first thing to go.

**D-phase7-3 · One `AlertKey` column serves every subject type; non-alert keys carry a type prefix (phase 7).**
The console table has no `SubjectType` column (AlertKey, ActionType, Actor, ActorRole, Unit, Note, OutcomeLabel, Payload, ClientTs). Alerts are stored bare (`A0001`, the 665 live ids are `A0001…A0665`); case / alias / face / ingest subjects are stored as `case:123`, `face:<searchId>`, `ingest:<batchId>` — which is exactly what the OCR-attach, face-identification and ingest modules already write — and `Payload.subjectType` repeats it. `GET /actions/recent?subjectType=case` narrows with ZCQL `LIKE 'case:*'` and a second in-process check. Alerts keep the strict vocabulary (six action types, five outcome labels, five dismiss reasons, notes ≤ 500 chars); other subjects accept any `[A-Za-z][\w-]{0,31}` action type and a free ≤ 32-char OutcomeLabel so their modules do not have to mirror this file, and `computeOutcomes` counts them in `bySubject`, never in alert precision.

**D-phase7-4 · Precision is true_positive ÷ labelled with a Wilson interval; `actioned` is not a true positive; no online learning is claimed (phase 7).**
`labelled` = alerts whose latest `outcome` row carries a label; `truePositive` = those whose latest label is `true_positive`. `actioned`, `already_known` and `no_action_needed` are shown in the mix but do not count as "real" — an alert can be acted on without the rise being real, and inflating precision is the one thing this panel must not do. The 95 % Wilson score interval is computed in `wilson(k, n)` (pinned in the suite: 3 of 10 → 0.108–0.603, the textbook values). The labels block states the retrain minimum (30 per class, 100 in all), the per-class shortfall and `onlineLearning:false`; the retrain path is `pipeline/analytics.py` re-run by a person with these labels as the evaluation set.

**D-phase7-5 · Time-to-acknowledge and staleness are measured from `AnomalyAlert.CreatedAt` on the server; the SLA hours mirror the client's `sla.js` (phase 7).**
The browser SLA badges count from the moment a console first listed the alert (`dappa-alerts-firstseen`), which differs per machine; the printed truth has to be the same everywhere, so the server measures from `CreatedAt` (falling back to PeriodEnd, then PeriodStart) to the first `acknowledge` row's `ClientTs`, and "stale" = OPEN, no acknowledge or dismiss row, older than the severity's window (band 3 → 4 h, 2 → 12 h, 1 → 24 h, 0 → 48 h — the same numbers as `SLA_HOURS` in `client/src/routes/alerts/sla.js`). Data Store datetimes are IST wall-clock strings; `parseTs` / `toDsDatetime` treat a bare `YYYY-MM-DD HH:MM:SS` as +05:30 on both sides so a Catalyst container (UTC) and this workstation (IST) compute the same hours.

**D-phase7-6 · The demo seed is 40 decisions on the oldest alerts, eight templates cycled, every Payload marked `source:"fixture"` (phase 7).**
`seedActions(alertRows, {count:40})` sorts alerts by CreatedAt, walks them in order and applies template `t mod 8` to alert `t mod n`: acknowledge/assign/note/outcome:true_positive · acknowledge/dismiss:duplicate · escalate/acknowledge/outcome:false_alarm · acknowledge/note/outcome:actioned · acknowledge/assign/escalate/note/outcome:already_known · acknowledge/dismiss:seasonal · acknowledge/outcome:no_action_needed · acknowledge/assign/outcome:true_positive. The first action lands 1, 3, 6, 12, 26, 2, 50, 5, 9, 0.5, 30, 4, 8 h after CreatedAt (cycling by alert index, +72 h per round) and each later step 30 min after the previous, so the time-to-acknowledge distribution has spread. Against the live table (`node scripts/seed_actionlog.mjs`: 665 alerts read from the Development API, oldest by period end) the seed touches A0001–A0013 once each — 40 rows, first row `A0001 acknowledge 2023-10-01 09:00:00` — and is written to `pipeline/out/ActionLog_seed.csv` (gitignored; the generator is tracked). Against the four-alert contract fixture the templates cycle four rounds, giving the hand-computed table the suite pins: AL-004 (oldest, ACK) 17 rows, latest outcome true_positive; AL-003 6 rows, dismissed three times (duplicate ×2, seasonal ×1 across rounds), never labelled; AL-002 escalated, latest outcome false_alarm; AL-001 latest outcome actioned. Totals: 13 acknowledge · 5 assign · 4 escalate · 3 dismiss · 6 note · 9 outcome; first-ack delays 1, 3, 6.5, 12 h → median 4.8 h; labelled 3, true positive 1 → precision 0.333, Wilson 0.061–0.792. Actors are `seed:sho-demo` / `seed:io-demo` / `seed:sdpo-demo` so no seeded row can pass for an officer's.

**D-phase7-7 · The Catalyst Mail digest is served as JSON and a printable page until a verified sender exists; `notify.py` is not extended (phase 7).**
`docs/CATALYST_SERVICE_RESEARCH.md` §4.11: a Gmail `MAIL_FROM` cannot be verified, so `MAIL_FROM` / `DIGEST_TO` stay empty in the tracked config and `POST /alerts/digest/send` returns `mode:'disabled'` (flag off) or `'not-configured'` with the full preview and `fallback.page:'/alerts/digest'`; with the flag on and a stubbed mailer the suite shows `mode:'sent'`, `source:'catalyst-mail'`. The digest keeps the `{subject, lines, text, html}` keys `lib/mail.js sendDigest` and `functions/dappa_nightly/notify.py build_digest` already use, so one shape serves the API, the page and the cron. The Python cron was left alone: composing the ActionLog section there needs a `store_catalyst.fetch_table('ActionLog', …)` read plus a fixture CSV for the dry run, which is a cross-function change with no harness in this phase; the nightly digest therefore carries alerts and risk only, and the action-loop digest is the API page. Console step for the lead: Notify → Mail → add and confirm a sender on a domain the team controls (SPF/DKIM), set `MAIL_FROM` and `DIGEST_TO` in the console env, flip `FEATURE_MAIL` — free tier 100 mails/month.

**D-phase7-8 · Web push is registered from the client only for a signed-in user; anonymous judges get the in-app notification centre fed by the same events (phase 7).**
§4.12: recipients are addressed by the account email and the client must call `catalyst.notification.enableNotification()` after sign-in. `client/index.html` does not load the Catalyst web SDK; `NotificationBell` injects the project's own `/__catalyst/sdk/init.js` on demand (served by Catalyst hosting, not a third-party CDN; it 404s on the vite dev server and the sheet says so) and then `POST /notify/register` with the email. The bell, the unread count (text + ▲ glyph) and the sheet work for everyone, polling `/alerts?status=OPEN` and `/actions/recent` every minute; an `escalate` or `assign` action also calls `push.sendPush` behind FEATURE_PUSH, and the suite shows `mode:'sent', delivered:1` with a registered recipient and `disabled` on the tracked config.

**D-phase7-9 · Alert cards fetch their decision timeline only when the officer opens the controls (phase 7).**
The live corpus is 665 alerts; showing recorded-decision chips on every card at load would be one `GET /alerts/:key/actions` per card. The card variant of `ActionControls` therefore enables its timeline query on first open (and after any decision), while the detail sheet always loads it. Consequence: a card whose controls were never opened shows no chips even if seeded decisions exist — the sheet and the outcomes panel are the complete views.

**D-phase7-13 · The card's quick Dismiss and the action-loop dismiss are two different writes; only one carries a reason (phase 7, corrected 29 Aug 2026).**
`Alerts.jsx doDismiss` (the card button, the detail sheet, bulk dismiss and the `d` shortcut) calls `setStatus.mutate({status:'DISMISSED'})` — a plain `AnomalyAlert.Status` write with no ActionLog row and no reason. The action-loop dismiss (`POST /alerts/:key/actions`) refuses without a reason and refuses `other` without a note. Both are legitimate: a triage sweep should not demand a taxonomy per row, and the audit trail should not be filled with `reason:'other'` placeholders. The consequence is stated on the feature line rather than hidden: the outcomes panel's DISMISSED count (ActionLog-derived) can be lower than the number of DISMISSED alerts in the feed, and the reason chart is the mix of the dismissals that were *recorded as decisions*. Routing the quick path through `useRecordAction` would need a reason picker on the bulk action too, which is a phase-4/alerts-owned surface; left as an explicit divergence, not a silent one.

**D-phase7-14 · An EMPTY ActionLog read falls through to the fixture in PUBLIC_DEMO, and says so (phase 7, added 29 Aug 2026).**
A FAILED ZCQL read already fell through to the fixture (D-phase7-1). An EMPTY one did not — and the deployed Development project has an ActionLog table that exists and was never seeded, so `/alerts/outcomes` returned `actionsInWindow:0`, `/alerts/digest` said "0 decisions recorded in 7 days" and every per-alert timeline was blank, while the contract suite and the static demo saw the 44 fixture rows. `readRows` now treats an empty result as a demo-mode fallback trigger, guarded three ways: only when `PUBLIC_DEMO` is on; only after a second `SELECT ROWID … LIMIT 1` proves the whole TABLE is empty (so a filtered read that legitimately matches nothing stays empty and stays `datastore`); and never again once any read has returned a row, so the probe is at most one extra query per container. `meta.storage` and `meta.source` report `fixture` and every row carries `source:'fixture'` — a fixture row is never presented as the Data Store's. This is a safety net, not a substitute: the lead should still run the seed (D-phase7-12), after which the fallback never fires.
