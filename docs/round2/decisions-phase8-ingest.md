# Phase 8 — data ingest (CSV → official ER schema) — decisions

Entries in `docs/DECISIONS.md` voice; the lead renumbers D-phase8-ingest-N → D-0NN.

**D-phase8-ingest-1 · Validation is always a dry run and the load is a second call; the file travels as JSON parts, not as a Stratus object (phase 8 ingest, 28 Aug 2026).**
`POST /ingest/validate` parses nothing itself — the browser's quote-aware
parser (`client/src/lib/csv.js`) sends `columns` + `rows` as JSON in parts of
≤ ~700 KB (`part:{batchId,index,final}`), the server validates every row and
returns `dryRun:true`; only `POST /ingest/load` writes. Why: the function's
JSON body limit (1 MB when this phase started, 6 MB after the faces phase
raised it) and a progress bar for a 5,000-row file both fall out of parts, and
a Stratus pre-signed PUT would have added a second upload path the officer
cannot see. Row 223's "Stratus pre-signed PUT or function multipart" is
therefore met by the function path only; row 233 (object-created Signal →
validate) was not built.

**D-phase8-ingest-2 · Batches live in the API container's memory for two hours (12 at most), and the screen says so (phase 8 ingest, 28 Aug 2026).**
No Data Store table exists for batches and tables are console-only
(`docs/CATALYST_SERVICE_RESEARCH.md` §4.1), so `lib/ingest.js` keeps validated
rows, verdicts, cursor and inserted ROWIDs in a bounded Map. A container
restart or a second container loses a batch; the client re-validates in one
call (`404 BATCH_NOT_FOUND` names the reason). The resume token is
`<batchId>:<cursor>` and a stale cursor is a `409 RESUME_MISMATCH`, never a
silent re-insert. Recorded so the batch history is not mistaken for a ledger.

**D-phase8-ingest-3 · Memory storage unless the admin token is present on the deployed API, and `meta.storage` names which (phase 8 ingest, 28 Aug 2026).**
The load gate accepts the District or State tier (`X-Dappa-Tier`, a
presentation claim per D-015) or the admin token. Data Store writes need
`zcatalyst-sdk-node.initialize(req)` AND the admin token — anything else loads
into the batch's memory so a judge on the default District tier can run the
whole flow, and the response says `storage:"memory"`. Why: PUBLIC_DEMO must
stay read-only for anonymous visitors (D-015, `requireAdmin`), and a demo that
pretended a memory load was a Data Store write would be the fake-service
label the brief forbids.

**D-phase8-ingest-4 · Out-of-district coordinates warn by default; only invalid and out-of-Karnataka coordinates reject (phase 8 ingest, 28 Aug 2026).**
Measured on 28 Aug against `pipeline/out/CaseMaster.csv` (45,000 rows) with a
ray cast over `data/geo/karnataka_districts.geojson`: 22 of 38 police units
have 100 % of their synthetic points inside their mapped census polygon, but
138 Bengaluru Rural South has 0 %, 129 Uttara Kannada 35.9 %, 102 Bengaluru
District 44.4 %, 105 Mangaluru City 66.1 %, 137 Vijayanagara 72.7 %, 117 Udupi
74.8 %, 124 Chikkaballapur 76.2 %. The 30 census polygons and the 38 units do
not align (commissionerates share a polygon; 2011 boundaries), so a strict
rejection would throw away real-looking rows. `GEO_OUT_OF_DISTRICT` is a
warning, `options.strictGeo` makes it a rejection, and `GEO_INVALID` /
`GEO_OUT_OF_STATE` (outside 11.5–18.5 N, 74.0–78.6 E) always reject. The
demo file carries one of each.

**D-phase8-ingest-5 · Foreign keys are checked against the live lookups unioned with a bundled copy of the masters, then a page read for what neither knows (phase 8 ingest, 28 Aug 2026).**
`assets/ingest_reference.json` (generated by `scripts/make_ingest_demo.mjs`
from `pipeline/out`: 38 districts, 359 units, 1,280 employees, 76 courts, 65
sections …) is unioned with `getLookups()`; values still unknown are looked up
with IN-chunked selects on the target's key (≤ 100 per query, ≤ 2,000 distinct
values, `partial:true` beyond). Why: the fixture holds 15 stub units and one
court (501), so the demo file's real station ids would all fail in fallback
mode, and the live `GET /meta/lookups` returned **321 units, not 359** on
28 Aug (`meta.source:"datastore"`, districts 38) — the bundled copy covers the
38 units the live Unit table does not hold. Live lookups win over the bundle
for a unit's district (fixture unit 1011 is Bengaluru City; pipeline unit 1011
is the Kalaburagi DPO).

**D-phase8-ingest-6 · Duplicate detection costs ⌈n/100⌉ selects per key and asks for district / unit ids in both padded and bare forms (phase 8 ingest, 28 Aug 2026).**
`storeKeys()` sends `WHERE key IN (…)` in chunks of 100 for CrimeNo and
CaseMasterID (or the table's key), so a 5,000-row CaseMaster batch is ≤ 100
Data Store selects. The masters hold `101` while the fact tables and the
fixture hold `'0101'` (lib/lookups.js), so a District/Unit key is asked for as
both and the answer is normalised with `dkey()`. The live Development store
answered `GET /meta/lookups` with `districtId:"101"` and `parentUnit:null`
on 28 Aug, which is the bare form this handles.

**D-phase8-ingest-7 · "What changed" is a projection from the accepted rows, and no batch AggMonthly upsert was added (phase 8 ingest, 28 Aug 2026).**
Before = `AggMonthly` `SUM(CaseCount)` / `SUM(HeinousCount)` for the anchor
month and the open-alert count (the `/summary/kpis` aggregates); after =
before + accepted rows dated in that month; the z per touched district ×
crime-head month is `lib/circuits.js robustZ` of the month total against the
trailing 11 months, alert line z ≥ 2 (docs/UX_RESEARCH.md §11 rule 3), top 12
pairs by row count. Why a projection: on the deployed store the CaseMaster
insert Signal already upserts AggMonthly per row and the nightly job
recomputes it exactly, and a memory load has nothing to upsert; a second
read-modify-write path would race the event function. Row 228 is therefore
partial and says so in the feature list. Live check 28 Aug: `/summary/kpis`
`asOfYm:"2026-07"`, `totalFirs:1151` — the demo's 188 accepted rows (183 clean plus
5 accepted with a note) are dated July 2026, so a live load projects
1,151 → 1,339, heinous 143 → 171 and month on month −11.3 % → +3.2 %
(measured through the client against the pipeline dataset, 29 Aug).

Two things made that projection read as nothing on the fallback dataset, and
both are fixed. `lib/fixture.js` built AggMonthly for the 36 months ending at
the *current* month while pipeline/out ends at the last complete one, so the
fixture anchored at 2026-08 while the bundled demo CSV is dated 2026-07: the
tiles read "485 → 485, delta 0" while month-on-month moved −7.4 → −31.9,
because the batch inflated the previous month only. The fixture's aggregate
and forecast windows now end at the last complete month like the real load, so
the fixture anchors at 2026-07 and validating the demo file reads 524 → 712
(+188), heinous 85 → 113, month-on-month −4.9 % → +29.2 %. Belt and braces:
`whatChanged` now also returns `kpis.batchMonth` — the same before/after for
the month the batch actually lands in — whenever that is not the anchor month,
and `WhatChangedCard` drives its count tiles off it, so a back-dated extract
can never show a still tile beside a moved percentage. Both are pinned in the
contract suite.

**D-phase8-ingest-8 · The privacy guard blanks caste / religion by default and the rejection report never carries a PII or narrative column (phase 8 ingest, 28 Aug 2026).**
`CasteMaster`, `ReligionMaster`, `ComplainantDetails.CasteID/ReligionID` are
accepted for schema fidelity (the ER is law), blanked before load unless
`dropSensitive:false`, and flagged `never-used` either way; name / DOB / KGID
columns are `pii` (loaded, never exported); extra headers matching caste /
religion / jati / dharma or phone / mobile / aadhaar / email / address /
passport / PAN / voter / DOB are dropped and reported per row. The CSV report
is row number + key columns + verdict + codes + details only — and the detail
is where the claim nearly failed: a type or date issue echoes the offending
cell, which is what makes the row fixable, so a dd-mm-yyyy `EmployeeDOB` on a
row rejected for an unrelated reason would have carried
`DATE_NORMALISED: 12-03-1965 → 1965-03-12` out with the file. A detail whose
column is `pii` or `never-used` now reads `redacted` while the code and the
column name stay, on the server report and on the browser-built one; the suite
checks the date of birth does not appear in the CSV.

**D-phase8-ingest-9 · The CCTNS IIF-1 preset ships flagged `verified:false` (phase 8 ingest, 28 Aug 2026).**
`docs/DOMAIN_RESEARCH.md` §2.1 verifies the seven Integrated Investigation
Forms; no export column list was found, so the preset's source names
(FIR_NO, PS_CD, …) are a guess. The registry, the picker and the mapping step
say "unverified" and tell the officer to check a real export first.

**D-phase8-ingest-10 · The ingest audit is a phase-7 `note` action on subject `ingest:<batchId>` (phase 8 ingest, 28 Aug 2026).**
`lib/actionlog.js recordAction` lists `ingest` as a subject type but its
action verbs are acknowledge / assign / escalate / dismiss / note / outcome,
so the load writes `actionType:'note'` with who / table / accepted / rejected /
storage in the note and payload. If the module is absent the SDK
`ActionLog.insertRow` is tried, then memory; the response's `audit.source`
names which path answered. In the harness (no SDK) `recordAction` stores in
memory and reports `actionlog`.

**D-phase8-ingest-11 · Rollback deletes only what this container can identify (phase 8 ingest, 28 Aug 2026).**
Memory batches never wrote a row anywhere: without the admin token `load`
walks the accepted rows, counts them and returns, so "rollback" marks the
batch rolled back and its rows stop counting as loaded. The response says so
rather than reporting `removed: n` as if n rows had been deleted from a table. Data Store
batches roll back only with the admin token and only by the ROWIDs
`insertRows` returned to this container, in `deleteRows` chunks of 200; if the
ROWIDs are gone (restart, other container) the call is a `409
ROLLBACK_UNAVAILABLE` that says to delete by CrimeNo / CaseMasterID in the
console. The AggMonthly increments the event function made are not reversed;
the nightly job reconciles. Delete requests are 1,000 / month on the free tier
(docs/CATALYST_SERVICE_RESEARCH.md §4.1).

**D-phase8-ingest-12 · The static demo validates in the browser and refuses to load (phase 8 ingest, 28 Aug 2026).**
`localValidate.js` runs the subset that needs no store (required, types,
limits, dd-mm-yyyy, digit grouping, CrimeNo structure, in-batch duplicates,
coordinate range, the guard) with `meta.source:'browser'` and a banner naming
every check it skipped — foreign keys, store duplicates, district polygons,
the CrimeNo district-vs-station cross-check, sub-head-belongs-to-head, the
load-order prerequisites and the before/after KPIs (the first version named
four of the seven). The browser has no district polygons at all, so every
in-Karnataka point lands in `unknownPolygon`; the profile now carries
`polygonChecked:false` and prints "n inside Karnataka but not checked against
a district polygon" instead of "0 inside their district", which read as a
finding rather than as a check that never ran; `GET /ingest/tables` comes from the snapshot
(`scripts/demo_snapshot.mjs`); loads throw `DEMO_STATIC`.

**D-phase8-ingest-13 · CrimeNo's category digit is compared with the row's CaseCategoryID, not with a fixed set (phase 8 ingest, 28 Aug 2026).**
`pipeline/out/CaseCategory.csv` holds ids 1, 3, 4, 8 while
`lib/constants.js` lists 1–4; the 45,000 pipeline CrimeNos start with 1, 3, 4
or 8 and every one equals the row's CaseCategoryID. The validator therefore
checks digit = CaseCategoryID and leaves the id set to the FK check.

**D-phase8-ingest-14 · Data Store value shapes on insert (phase 8 ingest, 28 Aug 2026).**
Doubles are sent as strings, Booleans as true/false (1/0, yes/no, y/n
accepted), Date as `YYYY-MM-DD`, DateTime as `YYYY-MM-DD HH:MM:SS` (a missing
time part becomes 00:00:00 with a note), Var Char lengths per
`docs/SCHEMA_CHECKLIST.md` capped at 255 and Text at 10,000, counted in code
points so Kannada text is not penalised. dd-mm-yyyy is read as day-first
(Indian convention, UX_RESEARCH §11 rule 5) and reported as `DATE_NORMALISED`.

The `/ingest` entry sits in the Records group under `/reports` with the
