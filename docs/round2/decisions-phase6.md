# Round 2 — Phase 6 decisions: face identification

D-entries in docs/DECISIONS.md voice (the lead renumbers). Every fallback and judgment call in `functions/dappa_api/lib/faces.js`, `lib/routes/faces.js`, `lib/png.js`, `scripts/faces_*.mjs` and `client/src/routes/identify/*`, plus what Zia actually returned (or did not) during the build.

**D-phase6-1 · Zia Face Analytics and Identity Scanner were NOT exercised live during this build; the path is coded against the SDK typings and stays flag-gated (phase-6 agent, 28 Aug 2026).**
`catalyst serve --http 3103 --only functions:dappa_api` was tried once and refused to start: "Error in running the pre cleanup process: unable to cleanup the .build directory" — the repo-level `.build` folder was held by another agent's serve, and retrying would have interfered with it. The SDK is initialised only from a request inside the Catalyst runtime, so no standalone script can reach Zia from the workstation. Consequently no analyseFace / compareFace response is recorded verbatim in this document; the calls are coded to the installed 3.4.0 typings (`analyseFace(fs.ReadStream, {mode}) → {faces_count?, faces[{confidence, co_ordinates, landmarks…}]}`, `compareFace(source, query) → {confidence, matched}` with `matched` compared as the STRING the docs show, docs/CATALYST_SERVICE_RESEARCH.md §5.1–5.2) and to the failure modes those docs describe. The exact live check the lead runs after `node scripts/deploy.mjs` (8 pooled Zia calls: 4 analyseFace + 4 compareFace on 2 gallery faces and their 2 probes) is
`node scripts/faces_zia_probe.mjs --base https://project-rainfall-60079891305.development.catalystserverless.in/server/dappa_api/api/v1 --token <ADMIN_TOKEN>`
— it writes `docs/benchmarks/face_zia_probe.json` verbatim, and the numbers belong in this entry. Until then every response from the deployed function honestly reports `gate.mode:'advisory'` / `meta.engine:'local-descriptor'` when the flag is off, and the contract suite exercises the flag-on path with a fake Zia client (detection, comparison, cached repeat, no-face, connection failure).

**D-phase6-2 · The local descriptor engine is the default and its confidence is a calibrated cosine, not a raw one (phase-6 agent, 28 Aug 2026).**
Catalyst offers no 1:N face search — Identity Scanner is strictly 1:1 (§5.1) — and the gallery is procedural, so a detector trained on photographs may not see it. The honest default compares the probe against each shortlisted candidate in the same parameter space the generator draws from (`lib/faces_spec.js`): the probe's own seed when it is one of ours (exact, 12 dimensions), otherwise pixel statistics measured by a zlib-only PNG decoder (`lib/png.js`) — background from the corners, skin from the centre patch, face extents from the skin-like rows, hair from the band above the face, as chromaticity + luminance so a re-lit capture moves one dimension — against the gallery image's stored pixel descriptor (`FaceGallery.QualityJson.pixel`, written by `scripts/faces_upload.mjs` with the same code). Raw cosine over these few dimensions crowds every pair into the top of the axis: the uncalibrated equal-error floor sat at 0.96. A fixed exponent (`LOCAL_SHARPEN = 8`, `confidence = ((cos + 1) / 2) ^ 8`) stretches that top so the equal-error region lands near the 0.7 floor Zia's scale uses; it is monotone (ranks unchanged) and the model card reports rates measured AFTER it. Measured by `node scripts/faces_calibrate.mjs` on the 200 generated faces (200 same-person probe-vs-gallery pairs, 1,000 different-person pairs per path): pixel/pixel — same-person median 0.9934 (p10 0.8762), different-person median 0.1526 (p90 0.6917), at floor 0.70 FAR 9.6 % / FRR 7.5 %, equal-error floor 0.73 (8.2 %); pixel/spec — FAR 11.4 % / FRR 7.0 %, EER floor 0.88; spec/spec — FAR 0.7 % / FRR 0, same-person 1.0 by construction. Shortlist rank test (25 candidates containing the true person, pixel/pixel): top-1 88.5 %, top-3 95 %, median rank 1, "no reliable match" 2 %, wrong person first above the floor 10.5 %. Twelve skin tones × six hair colours bound what pixels can separate; the filters and the human decision exist for exactly that reason, and the card says so.

**D-phase6-3 · One visible floor for both engines, default 0.70, dead band 0.10 (phase-6 agent, 28 Aug 2026).**
`FACE_MATCH_FLOOR` (env, tracked as "0.7" in catalyst-config — a policy value, not a credential) applies to whichever engine scored a candidate; Zia's own `matched` flips at 0.5 and is carried through as `zia.matched` but never decides anything. `bandFor()` labels ≥ floor as lead, [floor − 0.10, floor) as borderline, below as below; the search decision is `no-reliable-match` unless the top candidate is a lead, and the top figure stays visible with the floor beside it. A stricter floor turns the same search into "no reliable match" (pinned by the suite at 0.99). The alternative — a second, engine-specific floor (the local EER of 0.73) — was rejected because two floors on one screen defeat the "visible and configurable" promise; the calibration entry above records where the local engine's equal-error point actually is.

**D-phase6-4 · A shortlist needs a filter; district matches the live name dialect and the fixture id dialect; age and gender come from Accused rows (phase-6 agent, 28 Aug 2026).**
`POST /identify` returns 400 FILTER_REQUIRED with no district / MO / risk / age / gender / year filter — a whole-gallery sweep is refused rather than capped. Live `OffenderProfile.DistrictsJson` holds district NAMES ("Bengaluru City", verified on the deployed `/offenders`) while the fixture holds ids ("0101"), so the district filter runs `DistrictsJson LIKE '*<name>*'` first and retries with the id form only if nothing comes back; both are single bounded ZCQL queries (limit 200, ordered by RiskScore). `OffenderProfile` carries no age or gender, so those two filters are resolved through the `Accused` rows behind the shortlisted names (AccusedName IN (≤50), GenderID, AgeYear) — at most four IN-queries — and the response's `shortlist.applied` says they were applied that way. Backlog row 83's age estimate from `analyseFace` was not built: Zia may not detect a procedural face at all, and an estimate the gate cannot produce is not a filter.

**D-phase6-5 · Audit rows reuse the console's ActionLog columns; `SubjectType` lives in Payload (phase-6 agent, 28 Aug 2026).**
The `ActionLog` table the lead created (id 50643000000453003) has AlertKey, ActionType, Actor, ActorRole, Unit, Note, OutcomeLabel, Payload, ClientTs — no SubjectType column — so a face search is stored as AlertKey `face:<searchId>`, ActionType `face-search` / `face-decision`, Payload `{subjectType:'face', probeSha256, caseNo, legalBasis, filters, shortlist, candidates, topConfidence, topPersonKey, engine, gate, floor}`; the probe image is never written anywhere. Writes go through `datastore().table('ActionLog').insertRow` when the SDK initialises (deployed) and are mirrored into Catalyst Cache (`v1:face:audit`, 7 days) and a per-container ring, so the History tab is populated in every runtime; reads merge the three and mark each record's `source`. Phase-7's `lib/actionlog.js` landed mid-build with its own `recordAction(ctx, req, input, identity)` contract (SUBJECT_TYPES includes `face`, ACTION_TYPES has no "search"); a confirm / reject is therefore ALSO recorded through it as an `outcome` action (`true_positive` / `false_alarm`, subjectKey = searchId) so the action-loop statistics count face decisions, with the own row as the fallback. The fixture appends two demo searches and one confirm to `tables.ActionLog` (concat, never assignment, so the phase-7 seed survives).

**D-phase6-6 · Anonymous PUBLIC_DEMO visitors can search and decide; the audit records them as "anonymous (public demo)" (phase-6 agent, 28 Aug 2026).**
Alert acknowledgement is admin-gated, but a face search that judges cannot run is not a demonstration of accountability. The identity comes from `lib/auth.js whoami()` — a Catalyst session or the admin token yields the real actor and role; an anonymous visitor is recorded as `anonymous (public demo)` / `viewer` with `roleSource anonymous`. Every audit row therefore says exactly how much is known about who acted, which is the honest version of "recorded with the officer's identity" on a public demo. Purpose binding (case number + legal basis) is enforced for everyone.

**D-phase6-7 · JSON body limit raised to 6 MB on the face paths only (phase-6 agent, 28 Aug 2026).**
A 4 MB probe is ~5.4 MB of base64; the global 1 MB `express.json` gate would have turned the documented limit into a 413 before the route ran. Rather than lift the gate for every route, `lib/app.js` mounts a 6 MB parser on `/identify*` and `/admin/faces*` (both mount prefixes) ahead of the global 1 MB one; `express.json` skips an already-parsed body, so nothing else changes and the OCR body-limit pin in test/run.mjs still holds. `decodeProbe()` refuses > 4 MB with 400 PAYLOAD_TOO_LARGE before decoding. The client downscales every upload to ≤512 px and re-encodes as PNG (~100 KB), so the wide limit is rarely exercised.

**D-phase6-8 · Gallery thumbnails are SVG stand-ins; the Stratus PNG is touched only by Zia (phase-6 agent, 28 Aug 2026).**
`generatePreSignedUrl` needs a user context that an anonymous or admin-token call does not have ("No such User with the given id exists", index.js), so `GET /identify/thumb/:personKey.svg` renders the stored Seed through `lib/faces_spec.js` — the same drawing the Python generator made, as vectors — and the gallery / candidate / Offender-360 panels show that. The 512×512 PNG in Stratus (`face-gallery/v1/<PersonKey>.png`, bucket `STRATUS_BUCKET` = dappa-import) is fetched only inside `ziaCompare()` (memory-cached, ≤60 objects per container) and streamed to `compareFace`. No binary asset lives in the tracked tree except the three ≤11 KB test fixtures below.

**D-phase6-9 · Zia quota policy: at most 6 billed calls per search, 24 h comparison cache (phase-6 agent, 28 Aug 2026).**
Zia is a pooled 100 calls / month; a 25-candidate 1:1 sweep would be a quarter of it. With the flag on a search spends one `analyseFace` plus at most `FACE_ZIA_MAX_COMPARES` (tracked "5") `compareFace` calls on the top-N of the local pre-rank; the rest of the shortlist keeps its local figure and says so per candidate (`engine`, reason codes). Comparisons are cached in Catalyst Cache by probe sha256 + PersonKey for 24 h, so a repeated search costs nothing (pinned by the suite). `GET /identify/cost` and the line under the button show the spend before the search runs; total time budget 20 s, per-call `AI_TIMEOUT_MS`, parallelism 3.

**D-phase6-10 · Three small PNG test fixtures are committed (phase-6 agent, 28 Aug 2026).**
`functions/dappa_api/test/round2/fixtures/` holds two 160 px probes of fixture persons P001 and P004 (10.7 KB each, drawn by `pipeline/faces_generate.py --keys P001..P006` and downscaled) and a flat 322 B PNG. The suite needs real pixels to exercise the PNG decoder and the pixel path end-to-end; generating them at test time would need a rasteriser the function bundle does not have. `test/` is excluded from `catalyst deploy` (catalyst.json ignore).

**D-phase6-11 · Age / emotion / gender from Face Analytics are never requested (phase-6 agent, 28 Aug 2026).**
`analyseFace` is called with `{mode:'moderate'}` only — detection, confidence, box and the 5-point landmarks the pose proxy needs. The demographic estimates the API can return are not requested, not stored and not shown: they would be an inference about a person from a face, which is the line docs/DOMAIN_RESEARCH.md §6–8 draws, and the shortlist filters already have a records-based source for age and gender.

**D-phase6-12 · Backlog rows left out and why (phase-6 agent, 28 Aug 2026).**
Row 65 / 85 (alias verification by comparing two gallery images through Zia) — each pair is a billed call against a pooled quota already spent by searches, and on a procedural gallery the local engine answers the same question for free; the confirmed-face boost on the alias queue (row 80) ships instead. Row 67 (side-by-side landmark overlay) — the box is drawn on the probe; the candidate side has no landmarks without a second Zia call per candidate. Row 71 (ingest quality via analyseFace stored as Quality) — the upload script stores the measured pixel descriptor and `gate:'pending'`; a Zia pass over 200 images would spend two months of quota, so the gate on gallery images stays advisory. Row 86 (face-search PDF via SmartBrowz) — not built; the History tab prints. Row 83 — see D-phase6-4.

**D-phase6-13 · The visual 360×640 check was not completed in the browser (phase-6 agent, 28 Aug 2026).**
The built client and the stub API were served together on port 3103 and the /identify route was loaded in Chrome: the page, nav item, banner, tabs, upload card and form rendered and accepted values; the hidden-tab screenshot stayed at 896×326 and the window resize did not change it, so the 360×640 layout and the rendered results panel were not eyeballed. Layout classes follow the existing mobile-first patterns (single column below `xl`, 44 px controls, `overflow-x-auto` tables), and the results panel is exercised only through the contract suite.
